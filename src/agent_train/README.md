# Локальные траектории и обучение

Здесь находится реализация журналирования, аудита, экспорта SFT и небольшого
GRPO/QLoRA-пилота для Apple Silicon. По умолчанию используется уже скачанная
**Qwen3 0.6B, MLX 4-bit**. Загрузка конфигурации не запускает модель или GPU.

Из корня репозитория:

```bash
# Проверить итоговые настройки без обучения:
.venv/bin/python -m src.agent_train --config src/agent_train/configs/pilot.yml

# Проверить журналы и экспортировать подходящие train-примеры:
.venv/bin/python -m src.agent_train export data/eval/quality

# Подготовить отдельное окружение, если его ещё нет:
uv venv --python .venv/bin/python .venv-rl
uv pip install --python .venv-rl/bin/python -r src/agent_train/requirements.txt

# Только явный --train запускает обучение; папка результатов должна быть новой:
HF_HUB_OFFLINE=1 .venv-rl/bin/python -m src.agent_train \
  --config src/agent_train/configs/pilot.yml --train \
  --output data/training/runs/grpo-next
```

Экспорт по умолчанию пишет `data/training/trajectory-export`. Другие журналы можно
передать позиционными путями, например `.sea/coding`, или записать в
`train.datasets.trajectory_paths`. Известные диагностические задачи и траектории
без внешнего разрешения `training_eligible=true, split=train` исключаются;
пустая выгрузка допустима и не означает готовность к обучению.

## Конфигурации

| Файл | Назначение |
| --- | --- |
| [base.yml](configs/base.yml) | Все поддерживаемые настройки, Qwen3 0.6B |
| [pilot.yml](configs/pilot.yml) | 8 групп по 4 попытки; лимит между группами 10 минут |
| [grpo_long.yml](configs/grpo_long.yml) | До 200 групп / 2 часов; 16 контрольных задач, checkpointing |
| [sft.yml](configs/sft.yml) | До 100 шагов / 30 минут, обучение на проверенных текстовых траекториях |
| [coder_3b.yml](configs/coder_3b.yml) | Необязательная Qwen2.5-Coder-3B, MLX 4-bit; локально не испытана |
| [episodes.yml](configs/episodes.yml) | Многошаговый GRPO: search/read/edit/check/finish, до 8 действий на эпизод |
| [episodes_sft.yml](configs/episodes_sft.yml) | Короткий SFT-разогрев протокола на проверенных демонстрациях |
| [episodes_warm.yml](configs/episodes_warm.yml) | Свежие GRPO-эпизоды с начальным SFT-адаптером |
| [catalog/models.yml](configs/catalog/models.yml) | Справочник кандидатов, включая VL/Unsloth; не исполняемый конфиг |

`extends` наследует YAML с глубоким слиянием. Путь родительского конфига и
`project_root` считаются относительно определяющего их YAML. Пути модели,
данных и результатов — относительно `project_root`, независимо от текущего
каталога. CLI-параметры переопределяют YAML. В описании/манифесте верхние поля
показывают фактические настройки, `source_config` — исходный объединённый YAML.

Например, собственный профиль рядом с `base.yml`:

```yaml
extends: base.yml
train:
  steps: 40
  type_cfg:
    learning_rate: 3.0e-6
    num_generations: 4
  lora:
    cfg:
      r: 16
      target_modules: [q_proj, v_proj]
output:
  path: data/training/runs/custom-001
```

`model.path` должен указывать на локальную **квантованную MLX-модель**. Автозагрузки
нет. Для базовой 0.6B проверяется `download_manifest.json` с именем и revision.
При замене модели укажите её `name`, `path`, `revision`; `null` отключает проверку
манифеста (как у ещё не испытанного профиля Coder 3B).

LoRA rank, scale, target_modules, длины, sampling, KL, microbatch, learning rate,
лимиты памяти/кеша и checkpointing связаны с параметрами запуска. `scale` имеет
смысл MLX scale, а не PEFT alpha. В GRPO dropout равен нулю; накопление происходит
внутри одной группы, поэтому `gradient_accumulation_steps` здесь должно быть 1.
В SFT этот параметр работает как обычное накопление градиента.

`qat`, `use_vllm`, `bf16` должны оставаться `false`: QAT и PyTorch dtype overrides
здесь не реализованы, dtype берётся из MLX-весов. Внешняя reward-модель и OS-датасеты
не подключены. Неизвестные ключи и неподдерживаемые значения вызывают ошибку.
Поля sampling/KL/group/heldout относятся к GRPO, блок `train.sft` — к SFT.
В GRPO длина промпта проверяется без усечения; в SFT сумма prompt/completion
задаёт `max_seq_length` MLX-LM и может приводить к усечению длинных примеров.

## Что действительно обучается

GRPO обучает **одну арифметическую правку** с проверкой на 41 целочисленном входе
[-20, 20], через ограниченный AST-интерпретатор без исполнения сгенерированного
кода. Это ещё не обучение полной SWE-траектории или оркестратора. Используется
`inductive-mlxrl 0.3.0`: один unclipped update на свежую группу, нормализация наград
внутри группы и KL к замороженной базе. Группы с одинаковой наградой пропускаются.
Старые облачные ответы не выдаются за свежие on-policy rollout.

SFT ожидает `train.jsonl` с `messages` и последним текстовым ответом assistant.
`mask_prompt: true` исключает входной контекст из loss. `valid.jsonl` и `test.jsonl`
необязательны; совпадающие промпты между разделами отклоняются. Семейства задач
нужно разделять отдельно: такая проверка не выявляет все смысловые утечки.
Без `valid.jsonl` MLX-LM обучает без validation; test не запускается этим профилем.
Native tool calls пока не поддерживаются в SFT-шаблоне.

GRPO сохраняет manifest, реальные token IDs и logprobs, награды, метрики,
адаптер и проверки до/после. SFT сохраняет `sft-job.json`, `training.log` и штатные
MLX-LM checkpoints. Повторный запуск в существующую папку запрещён. Лимит GRPO
проверяется между группами, SFT ограничен таймаутом дочернего процесса; лимит памяти
MLX не равен общему расходу RAM системы.

В предыдущем коротком пилоте 0.6B обновление весов работало, но результат на трёх
контрольных задачах ухудшился с 1/3 до 0/3. Адаптер не включён в агента. Длинный
профиль задаёт бюджет эксперимента и не обещает роста качества. SFT теперь также
проверен на синтетических демонстрациях многошаговых действий, описанных ниже.
Подробнее: [отчёт по пилоту](../../docs/local_coding_harness.md).

## Многошаговые эпизоды

`episodes.py` создаёт отдельный маленький проект для каждой попытки. Модель сама
выбирает `tree`, `search`, `read`, `edit`, `check` и `finish` в JSON-протоколе
основного харнесса. Поиск и чтение возвращают реальные файлы; правки меняют только
копию этой попытки. Это отдельный учебный цикл, не полный `CodingHarness` с
наблюдателями и сабагентами.

Учебная задача — найти `transform(x)` среди нескольких файлов и исправить функцию.
`check tests` проверяет публичные входы -2, 0, 2. После завершения отдельный оценщик
проверяет все 41 вход [-20,20] и сохранность остальных файлов. Код разбирается
ограниченным AST-интерпретатором: shell, Docker и произвольный Python не исполняются.
Это обучение работе с инструментами на ограниченном арифметическом наборе,
не SWE-bench и не доказательство качества на произвольных программах.

Награда равна 1 только при корректном конечном состоянии и принятом `finish`
после успешного `check` актуальной версии файлов. Порядок поиска/чтения не зашит
в цикл; наград за число вызовов, чтение или заявления об успехе нет. Изменённые
тестовые данные, старые проверки и подгонка только под публичные входы не дают
успех. Ошибки модели возвращаются как наблюдения. Ошибки инфраструктуры прерывают
запуск; прерванные группы не превращаются в отрицательные обучающие примеры.

Для маленькой модели предусмотрен SFT-разогрев перед RL:

```bash
# Создать 24 проверенные учебные задачи / 120 примеров; без вызовов модели:
.venv/bin/python -m src.agent_train bootstrap

# Обучить формат и базовые последовательности на этих примерах:
HF_HUB_OFFLINE=1 .venv-rl/bin/python -m src.agent_train \
  --config src/agent_train/configs/episodes_sft.yml --train

# Обучаться на собственных свежих попытках после SFT:
HF_HUB_OFFLINE=1 .venv-rl/bin/python -m src.agent_train \
  --config src/agent_train/configs/episodes_warm.yml --train
```

Каждая команда требует новой выходной папки. Для повторения укажите `--output`;
при смене пути SFT-адаптера обновите `model.init_adapter` в GRPO-профиле.
Без `--train` два последних вызова только печатают настройки. Базовый запуск
без SFT использует `episodes.yml` и `model.init_adapter: null`.

Демонстрации имеют источник `scripted_expert`: действия составлены программно,
исполнены и независимо проверены. Они подходят для SFT и **не являются on-policy
rollout**. В них отсутствуют выдуманные logprobs. В SFT и RL train входят семейства
clamp/affine; distance оставлено для контроля. Такой небольшой контроль не
подтверждает общее качество и не используется для подбора гиперпараметров.

В GRPO одна группа — несколько независимых попыток одной задачи до любого
обновления весов. Нормализация наград выполняется по эпизодам. Полученное
преимущество применяется к действиям эпизода с их фактическим контекстом, token IDs
и logprobs. Выводы инструментов, системный промпт и пользовательские сообщения
исключены из целей loss. Используется среднее по токенам действий: длинный эпизод
содержит больше обучаемых токенов. Точное распределение заслуги по отдельным шагам
здесь не реализовано. Одинаковые награды всей группы дают нулевой сигнал и пропуск.

Температура и top_p в обучающих эпизодах равны 1, поэтому сохранённые logprobs
соответствуют распределению сэмплирования. Контроль использует greedy decoding.
KL сравнивает с исходной замороженной базой, включая запуск после SFT. При загрузке
начального адаптера проверяются модель/revision, rank/scale/dropout, имена и
размеры всех тензоров. Предвычисление reference выполняется по одному действию
для ограничения памяти, backward — с настроенным microbatch.

Результаты: `manifest.json`, `episodes/<group>/<candidate>/episode.json` с контекстом,
действиями, наблюдениями и финальными файлами; `metrics.json`, `group-*-behavior.npz`,
`before.json`, `after.json`, `summary.json`, LoRA-адаптер. Прерывание и неполная
контрольная выборка отражаются явно. Адаптер автоматически в основного агента
не устанавливается. Лимит времени проверяется между действиями/группами, не внутри
одной операции Metal.

Проверка реального градиента на крошечной MLX-модели без скачивания весов:

```bash
.venv-rl/bin/python scripts/check_episode_backend.py
```

Проверенный запуск 2026-10-31 на Qwen3 0.6B / M4 Pro:

| Этап | Результат |
| --- | --- |
| База, без SFT | 0/32 успешных train-эпизодов, 0 обновлений; 117.94 s |
| SFT-разогрев | 24 scripted train-задачи, 120 примеров, 80 шагов |
| Свежие GRPO-эпизоды после SFT | 10/32 успехов в процессе обучения, 4 обновления; 161.85 s |
| Контроль distance после SFT / после GRPO | 0/3 → 0/3 |

Успехи в ходе обучения не являются независимой оценкой качества. Этот эксперимент
подтверждает работающий цикл действий и обновления; переноса на новое семейство
он не показал. Отдельного сравнения SFT и SFT+RL при равном бюджете здесь нет.
Пик памяти MLX в GRPO после SFT — 1.601 GiB; это не полное потребление системы.
Сохранённый адаптер повторно загружен MLX-LM, все тензоры проверены на совпадение.
В раннем логе `mean_reward` библиотеки усредняет строки действий: долю успешных
эпизодов следует считать по `rewards`. Текущий код именует эти метрики отдельно.

[Машиночитаемый итог](../../data/training/tool-episodes-integration-summary.json)
содержит ссылки на журналы, контрольные результаты и проверку градиента.
Офлайн-регрессия: 1197 passed, 3 skipped, 12 warnings. Обучающие процессы завершены;
адаптеры не установлены в основного агента.

## Небольшие Coder и VL

Для следующего текстового эксперимента подготовлен профиль
[Qwen2.5-Coder-3B-Instruct-4bit](https://huggingface.co/mlx-community/Qwen2.5-Coder-3B-Instruct-4bit).
Это текстовая кодовая модель в MLX, без обработки изображений.

Для изображений и текста есть
[Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B) и её
[GGUF-кванты Unsloth](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF/tree/main).
На 2026-10-31: UD-Q4_K_XL — 2.91 GB, UD-IQ2_M — 1.76 GB,
UD-IQ2_XXS — 1.52 GB; vision projector F16 отдельно около 0.672 GB.
Это размеры файлов, не оценка полной памяти исполнения. Для первого сравнения
на 24 GiB я бы выбрал 4-bit: качество 2-bit именно на наших задачах не измерено.
Это общая мультимодальная модель, не специализированная модель семейства Coder.

Unsloth здесь предлагает готовые квантованные веса. GGUF служит для инференса
через llama.cpp; его нельзя напрямую обучать текущим MLX QLoRA-запускателем.
Для VL-обучения потребуется отдельный совместимый backend, процессор изображений
и датасет. Кандидаты не скачивались и не обучались в рамках переноса.
Исходный пользовательский VL-черновик сохранён в
[drafts/original_vl.yml.example](configs/drafts/original_vl.yml.example).

## Структура и совместимость

`trajectory.py` — журнал; `dataset.py` — аудит/экспорт; `verified_edits.py` — награда;
`grpo.py` и `sft.py` — обучение; `config.py`, `preflight.py`, `cli.py` — запуск.
Веса и результаты остаются в `data/`, журналы агента — в `.sea/`.
Старые `scripts/train_local_grpo.py`, `scripts/trajectory_dataset.py`,
`src.coding.trajectory*`, `src.training.verified_edits` — обёртки совместимости.

Проверка изменений без MLX/GPU:

```bash
.venv/bin/python -m pytest -q tests/test_agent_train_config.py \
  tests/test_training_trajectories.py tests/test_verified_edit_training.py
```
