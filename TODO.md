Симптом: «сделай git push» сожгло **196 720 входных токенов** (~$0.054) за один прогон.

Диагноз (не баг логики — перебор оркестрации + не кэшируется префикс):
- SEA.md/MEMORY.md **НЕ виноваты** — SEA.md ~1.1k токенов, MEMORY.md крошечный.
- 196k входных = **сумма по всем LLM-вызовам прогона**. «git push» прошёл полный граф
  (recall → reflexion → goal → router → **decompose → шаги** → synthesize → reflect), и каждый
  вызов заново шлёт весь контекст (system + tool-схемы + память + история + накопленные выводы
  git-команд). ~12–15 вызовов × ~14k = ~196k.

Два рычага:
1. **Префикс-кэш — ✅ ПРОАНАЛИЗИРОВАН (2026-06-17): уже structurally сделан там, где важно.**
   Самый горячий промпт `step_execution` (зовётся на КАЖДЫЙ шаг) cache-дисциплинирован: статичные
   правила впереди → длинный стабильный префикс (авто-кэш Gemini), динамика `{memory_context}…
   {step_feedback}` в КОНЦЕ (prompts.py:511-549). Остальные промпты (reflexion/act/router) держат
   `{memory_context}` в начале, НО зовутся раз-за-прогон → внутри прогона переиспользовать нечего.
   ВЫВОД: реальный драйвер 196k — НЕ кэш, а число вызовов + растущий хвост (история/результаты шагов
   пересылаются каждый вызов; кэшируется только фикс-префикс). Дальше — только с ПЛАТНЫМ замером
   (`/diagnose` → `cached` на живом прогоне), иначе тюнинг вслепую. **Реордер once-per-run промптов —
   маргинален, делать только если замер покажет кросс-прогонный кэш-промах.**
2. **Короткий путь для тривиального шелла.** ⚠ NB: «git push» был РЕАЛЬНО многошаговым (разбор `.pdb`
   в gitignore → git rm --cached → commit → push) — decompose тут по делу, не перебор. Этот рычаг
   применять к ИСТИННО тривиальным («покажи время», «привет»), не к git-цепочкам. Подкрутить
   reflexion/router/run-budget. Риск: недо-думать реальные задачи → тюнить с замером.

Итог: функционально ок; стоимость частично ВНУТРЕННЯЯ для многошаговой агентной работы. Главный
кэш-рычаг (горячий per-step промпт) уже на месте. Дальнейшее — мерить, не угадывать.

### Идеи по стоимости (по убыванию ценности; драйвер = N вызовов × растущий хвост)
- **A. ЗАМЕРИТЬ кэш-hit-rate первым** (платный прогон, `/diagnose`→`cached`). Если gemini-flash-lite
  через OpenRouter реально кэширует стабильный префикс на 12-15 вызовах прогона → ~10× по входу
  почти бесплатно. БЕЗ замера остальное — вслепую. **Это шаг 0.**
- **B. Резать растущий ХВОСТ** (он, а не префикс, доминирует в 196k). После завершения шага —
  заменять полные выводы тулов на 1-строчное РЕЗЮМЕ в последующих вызовах (есть within-step masking
  + `_compress_tools` cap — усилить: «свёрнуто: шаг N сделал X»). Терсить verbose git-вывод (списки
  файлов) перед подачей в следующий шаг.
- **C. Меньше ВЫЗОВОВ:** (1) валидацию шага зовём не на КАЖДЫЙ шаг, а только на рискованные/
  side-effect; (2) батчить тривиальные последовательные шелл-шаги в один вызов (а не LLM-на-шаг);
  (3) рецепт-реюз уже есть (sim≥0.7 → decompose БЕЗ LLM) — холодный «git push» рецепта не имел,
  тёплый будет дешевле.
- **D. Минимизировать tool-set на вызов:** JSON-схемы тулов шлются каждый вызов и большие;
  skill_selector уже сужает — догнать так, чтобы в step-вызов шли ТОЛЬКО релевантные тулы (меньше
  префикс). 
- **E. Дешёвая модель для дешёвых под-вызовов:** роутинг/валидация/экстракция уже на `fast`;
  проверить, не уходит ли тривиальный шаг на дорогой `code`-тир без нужды.
- **F. Реордер once-per-run промптов** (reflexion/act/router: `{memory_context}` в начало → в конец).
  Маргинально внутри прогона, делать ТОЛЬКО если замер (A) покажет кросс-прогонный кэш-промах.

Порядок: A (замер) → B (хвост) → C (вызовы). Не тюнить вслепую — риск недо-думать реальные задачи.

## 4. ИССЛЕДОВАНИЕ — DSPy/GEPA поверх своего контура? (идея, 2026-06-17)

Самооптимизация у нас — **онлайн, по трейсам, per-user, через TextGrad** (textual gradients по
виноватым нодам, `improve/graph_learn.py`). Это та же СЕМЬЯ, что DSPy, но не DSPy (DSPy = офлайн-
компилятор пайплайна под trainset+метрику; у нас — continual из собственных эпизодов). Идея на
прикидку: подмешать DSPy/GEPA как **офлайн-компилятор СТАРТОВЫХ промптов нод** (холодный старт
лучше), а онлайн-TextGrad-контур оставить для дообучения под юзера. Оценить: даёт ли это прирост
vs сложность интеграции (DSPy ↔ LangGraph-ноды). Не делать вслепую — сперва замерить cold-vs-warm.
