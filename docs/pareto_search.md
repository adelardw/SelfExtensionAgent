# Отбор конфигураций харнесса по качеству и расходу

С 5 ноября сводки также содержат `reliability`: наблюдаемые `pass_at_k`, `pass_power_k`, список нестабильных задач и долю задач с ложным завершением хотя бы в одном повторе. `deployment.consistency_floor` опционально задаёт минимальную долю задач, прошедших **все** повторы. Значение по умолчанию — `null`; старые критерии выбора сохраняются. Дробные оценки не превращаются в бинарный успех. Формулы и ограничения: [разбор оценки стабильности](harness_review_20261105.md#14-новая-проверка-стабильности).

Добавлен отдельный офлайн-цикл сравнения конфигураций SEA. Он использует настоящую цепочку `quality_ladder`: модель, инструменты, независимые проверки результата и сохранение траекторий. В основном цикле агента новых модельных вызовов нет.

Идея взята из [ParetoSaddler, arXiv:2611.02079](https://arxiv.org/html/2611.02079v1): допуск кандидата к дальнейшему изучению отделён от выбора версии для эксплуатации. Для сравнения повторов используется Bayesian bootstrap с одинаковым весом качества и стоимости каждого исполнения; задачи имеют равный вес. Сохраняются все прошедшие development-оценку варианты, включая варианты вне текущего Парето-фронта. Это собственная реализация, код авторов не копировался.

Наш пилот отличается от статьи: оптимизируется **общее число токенов**, а не денежная стоимость по фиксированному прайс-листу; временный рост допускается максимум на 50%. Цена USD сохраняется отдельно и ограничивается бюджетом. Токены не равны деньгам: кеширование и тарифы меняют их соотношение. Готовые изменения задаются небольшим планом; модель-оптимизатор, генерирующая патчи, не добавлена.

Дополнительно требуется реальное улучшение хотя бы одного наблюдаемого среднего. При положительной корреляции качества и расхода мягкое bootstrap-условие «улучшилось одно при допустимой потере другого» может иметь высокую поддержку даже у одинаковых эмпирических распределений. Отдельная регрессия воспроизводит этот случай; он не допускается к дальнейшим платным прогонам. Это наша дополнительная проверка, не точное воспроизведение правила статьи.

## Как проходит поиск

1. Проверяется `experiments/pareto_pilot.json`. Варианты наследуют разрешённые настройки родителей. Модель, провайдер, бюджеты, права инструментов и проверяющий одинаковы.
2. Baseline проходит `screen` и `dev`. Каждая задача исполняется трижды в новом workspace. Смена seed создаёт другую задачу и не считается повтором.
3. Кандидат сравнивается с повторами родителя на `screen`. При поддержке bootstrap ≥0,7 он допускается на `dev`. Это поддержка события улучшения на наблюдаемых задачах, не вероятность успеха на всех будущих задачах.
4. Кандидат сохраняется вместе с родителем, конфигурацией, снимком исходников, результатами и причиной отбора. Более дорогой промежуточный вариант может стать родителем следующего. Отклонённая ветвь не покупает dev-прогоны и не порождает зависимого кандидата.
5. На `dev` выбирается самый экономный допустимый вариант: средний успех ≥0,7, успех каждого домена ≥0,5, ложное «готово» = 0, среднее время ≤180 секунд, средний расход ≤80 000 токенов.
6. Выбор записывается **до** запуска `test`. После тестовой неудачи другие кандидаты по этой выборке не подбираются. Проверяются другие семейства задач. Они уже есть в репозитории и являются диагностическими, а не секретным публичным бенчмарком.

| Вариант | Родитель | Изменение |
|---|---|---|
| `baseline` | — | Адаптивный план, память результатов, адаптивный набор инструментов |
| `prefetch` | baseline | До 2400 байт исходников перед первым модельным чтением |
| `prefetch_completion` | prefetch | Предложение завершения после проверок с обычным независимым review |

Остальные условия берутся из зафиксированного профиля `quality_ladder`, включая одну модель для актёра/критика и проверку ответов. Это отдельный экспериментальный профиль, а не утверждение об идентичности продуктовым настройкам. Полная оценённая конфигурация сохраняется вместе с выбранными настройками.

| Этап | Математика | Алгоритмы | Программирование |
|---|---|---|---|
| screen | условное ожидание | вершинное покрытие | LRU-кеш |
| dev | цепь Маркова | пути в DAG | топологический порядок |
| test | надёжность сети | назначение с ограничениями | атомарные изменения SQLite |

## Запуск и расход

```sh
# Чтение локальных отчётов; без запросов к модели.
uv run python scripts/harness_search.py audit --reports data/eval

# План, настройки и максимальный резерв; без запросов к модели.
uv run python scripts/harness_search.py plan

# Настоящий эксперимент через существующий OpenRouter backend.
# Нужны действующий доступ и баланс. Каталог обязан быть новым.
uv run python scripts/harness_search.py run --live \
  --config experiments/pareto_pilot.json \
  --output data/eval/pareto-new-run
```

Без `--live` команда `run` только показывает план. Пилот: максимум 63 исполнения, резерв **$1,26** при лимите **$1,30**, до 180 секунд на задачу и до 30 минут на кампанию. Полный бюджет группы резервируется на диске до её запуска; экономия предыдущих групп не покупает дополнительные исполнения. При исчерпании времени/бюджета поиск останавливается с сохранением данных. Провайдерские оценки не являются гарантией биллинга; превышение резерва обнаруживается и останавливает продолжение.

Смена кода/базовой конфигурации, неполный отчёт, повторный ID исполнения, неопределённый расход или инфраструктурная ошибка запрещают сравнение. Старые файлы не перезаписываются. Прерванная кампания не возобновляется автоматически: резерв и частичные результаты сохраняются в `archive.json`; новый запуск требует нового каталога и нового явно заданного бюджета.

В каталоге кампании сохраняются:

- `archive.json`: план, резерв, происхождение кандидатов, все решения, dev-фронт и выбранная версия;
- `<variant>/<stage>/repeat-*.json`: исходные отчёты `quality_ladder`;
- `selected-profile.json`: полная оценённая конфигурация, ID исходников и протокола, итог теста. Файл не изменяет `config.yml`; `eligible_for_manual_adoption` — итог диагностики, не гарантия универсального качества.

## Проверка 4 ноября 2026

Аудит `data/eval` нашёл **78 прежних отчётов**, исключённых из отбора: в них нет полного нового протокола идентификации исполнений. Групп пригодных повторов — **0**. Старые результаты остаются полезными для диагностики, но не получают выдуманную статистическую уверенность. Новый `quality_ladder` записывает версию схемы, уникальный `run_id`, хеш проверяющего протокола и ожидаемый набор задач.

| Область | Проверки в `tests/test_pareto_search.py` |
|---|---|
| Статистика | Повторы, нулевой расход, границы регрессии, воспроизводимость bootstrap, совместное взвешивание качества/расхода |
| Качество | Дешёвый провал, ложное завершение, провал отдельного домена |
| Достоверность | Копии отчётов, смена модели/исходников/прав, неполная сетка, неопределённый расход |
| Цикл отбора | Сохранение промежуточного кандидата, отбрасывание ветви, фиксация выбора до теста, отказ после тестовой неудачи |
| Бюджет и состояние | Резерв до вызова, остановка при лимите и изменении исходников, сохранение частичных результатов |
| Интеграция | Настоящий reporter `quality_ladder` выдаёт данные, принимаемые новым загрузчиком |

**26 новых тестов; полный набор до последней статистической регрессии — 1292 passed, 3 skipped.** Ответы модели в новых тестах заменены контролируемыми fixtures. Это проверка механизмов отбора, а не измерение улучшения агента. Платный поиск в этой доработке не запускался: последний известный OpenRouter-запуск остановился с HTTP 402. Для утверждения о приросте нужны новые живые повторные прогоны; улучшение Flash/9B пока не заявляется.
