# Уточнения во время работы: источники и живая проверка

06.11.2026. Исследованы способы доставки сообщений и изменения намерения пользователя.
Затем проверен экспериментальный разбор сообщений через авторизованный Codex CLI.
Итог первого прогона — **16 точных совпадений из 20 сценариев**. Реальная модель
возвращала решения, локальный код проверял и применял их к состоянию задач без внешних
эффектов. Это проверка маршрутизации и обновления состояния, не SWE-bench и не готовый
постоянно работающий Router.

## Как скорректировать нашу конструкцию

Разделить три вопроса: **смысл изменения**, **момент доставки**, **управление исполнением**.
Например, «после A подготовь отчёт, A пока не прерывай» создаёт зависимую задачу,
ожидающую A, и сохраняет текущую политику исполнения A. Из этой фразы не следует новое
обязательное свойство результата A с названием «продолжать работать».

Уточнение пользовательского намерения превращается в дельту с исходной цитатой и
ссылками на требования. Runtime проверяет существование ID и ожидаемую версию состояния.
Неизменённые требования сохраняются кодом, а не восстанавливаются заново моделью.
Модель предлагает смысловую операцию; она не назначает себе инструменты, разрешения
или подтверждённость собственных выводов. Изменение зависимости должно инвалидировать
результаты потребителей; при неполном учёте зависимостей нужен консервативный охват.

Внутри задачи нужны разные состояния ожидания: завершение назначенного предшественника,
измеримое условие окружения и ответ человека. Их нельзя сводить к одной строке «ждём».
У очереди доставки должны быть квитанции по ID события. Принятие сообщения транспортом
не доказывает его присутствия в запросе конкретного работника и тем более понимания.

Текущий SEA уже отсекает часть старых генераций по версии steering и сохраняет память
при переключении профиля. Но ещё нет единого журнала задач, перезапуска диспетчера,
семантической маршрутизации в рабочем API и точного анализа зависимостей требований.
Они не появились автоматически от добавления этого экспериментального оценщика.

## Что именно проверялось через Codex

Команда `codex login status` подтвердила авторизацию через ChatGPT. Использован имеющийся
`CodexInference` из `scripts/codex_behavior_eval.py`: CLI возвращает один структурированный
ответ, ему запрещены собственные инструменты. Журнал проверяет отсутствие инструментальной
активности. Ключи и содержимое файлов авторизации не извлекались. Такой режим программного
запуска описан в [официальной документации Codex](https://learn.chatgpt.com/docs/non-interactive-mode).

Созданы:

- `src/eval/refinement.py`: типизированное предложение, проверка ссылок и происхождения,
  атомарное изменение копии состояния, отказ устаревшему решению и дедупликация события.
- `src/eval/refinement_cases.py`: 18 заранее размеченных независимых примеров.
- `scripts/refinement_eval.py`: шесть запросов по три примера и два последовательных
  запроса, где второй получает фактическое состояние после первого.
- `tests/test_refinement.py`: регрессии сохранения ограничений, приоритетов, отложенных
  условий, отмены одной задачи, недоверенного источника и отказа всему неверному плану.

Правильные ответы не отправлялись модели. Исходные примеры и точный prompt сохранены
перед вызовами. Сценарии охватывали добавление, замену, снятие, смягчение требования,
независимую и зависимую задачи, составные сообщения, двусмысленность, отрицание,
отмену, внешнюю инъекцию, цитату и условное действие.

Проверки соответствия ограничены точным совпадением структурных полей и явно заданных
значений в тексте; это не полный семантический oracle. Работники, браузер, файлы проекта
и длительные команды в этом эксперименте не запускались. Прототип сохраняет журнал
только в памяти; проверка повторного события не доказывает восстановление после сбоя.

## Первый результат и обнаруженные ошибки

| Проверка | Первый прогон |
|---|---:|
| Точное совпадение с размеченными операциями | 16 / 20 |
| Прохождение структурных runtime-проверок | 20 / 20 |
| Сохранение незатронутых прежних требований | 20 / 20 |
| Повтор события без второго изменения состояния | 20 / 20 |
| Вызовы Codex | 8 |
| Входные токены по CLI receipts | 145 533 |
| Выходные токены по CLI receipts | 2 435 |
| Долларовая стоимость | Неизвестна; не объявляется нулевой |

Четыре расхождения просмотрены отдельно:

1. **`cancel`:** правильная отмена A и дополнительная запись `context`, что B продолжает
   работу. Состояние B не изменилось. Это несовпадение строгой формы, не неправильная отмена.
2. **`dependent`:** завершение A указано и в `depends_on`, и в `condition`. Прототип
   поставил работу в общий список ожидания условия вместо нормальной зависимой задачи.
   Нужны однозначные типы ожидания и правила заполнения полей.
3. **`followup`:** отчёт правильно выделен отдельно, но «сейчас её не прерывай» добавлено
   как hard requirement к A. Это лишнее изменение контракта и потенциальная инвалидизация.
4. **`negation`:** B правильно отменена, но «не останавливай A» также превращено в новое
   hard requirement A. Управление жизненным циклом смешалось с критериями готовности.

Именно поэтому 20/20 сохранённых старых требований не означает 20/20 корректных
изменений: можно сохранить старое и одновременно добавить лишнее. Структурная
валидация также не распознаёт эти смысловые ошибки.

После просмотра добавлен отдельный `ROUTING_PROMPT_V2`: он явно отделяет подтверждение
продолжения от нового требования и завершение зависимости от дополнительного условия.
**На момент этого первого отчёта V2 ещё не был проверен живой моделью.**
Обновление 7 ноября: [исправление и отдельный опыт отбора промптов](reflective_prompt_search.md)
содержат повторную регрессию и новые отложенные примеры. Первый prompt, результаты и оценка 16/20 сохранены;
ошибочные ответы не исправлялись задним числом. Следующий прогон должен включать новые
отложенные формулировки, иначе это будет лишь проверкой исправления на известных примерах.

Транспорт — CLI 0.166.0-alpha.6 с моделью по умолчанию. Конкретный идентификатор backend
не зафиксирован в использованных receipts, поэтому здесь нет утверждения о конкретной
GPT-6-модификации. Это не проверка Flash/9B. Расход включает контекст оболочки CLI,
cached input по журналу равен нулю; переносить этот расход на будущий короткий Router
напрямую нельзя. Измеренные 147 968 токенов уложились в предел 180 000.

## Воспроизведение и следующий шаг

Без модельных вызовов:

```sh
.venv/bin/python scripts/refinement_eval.py
.venv/bin/python -m pytest -q tests/test_refinement.py
```

Новый оплачиваемый/квотируемый прогон требует явного `--live` и новой выходной папки:

```sh
.venv/bin/python scripts/refinement_eval.py --live --policy v2 --output data/eval/refinement-v2-new-trial
```

Протокол не подключён к рабочему endpoint steering. Сначала нужны измерения адресатов
и конечных действий на новых примерах, затем доставка в несколько активных ветвей с
проверкой версии, а после — постоянный Router. В эксперименте есть 20 небольших
сценариев по одному прогону; из них нельзя получить надёжный процент качества
универсального агента или оценить выигрыш над текущим харнессом.

Артефакты первого прогона: `data/eval/refinement-20261106/live/`: `protocol.json`,
`cases.json`, `result.json`, `analysis.json`, `transport-metadata.json`, запросы и ответы
`calls/call-*/`. Общие проверки находятся в `data/eval/refinement-20261106/`.

Офлайн-регрессии нового прототипа: **18 passed**. Полный набор репозитория:
**1351 passed, 3 skipped**, 12 предупреждений, 48,44 секунды. `git diff --check`
прошёл. Целостность подтверждена для 270 файлов после адресного добавления двух новых
модулей оценщика; исходная база сохранена в `integrity-before.json`.
