# Улучшение harness по проверенным траекториям

7 ноября 2026. Реализован ограниченный офлайн-цикл: история → отбор пригодных
примеров → предложение короткой дельты промпта → сравнение кандидатов → фиксация
победителя → отдельный test. Первое применение — уточнение задач и маршрутизация
намерений в `ShadowRouter`. Рабочий агент не делает новых фоновых вызовов модели.

## Что взято из исследований и других harness

| Источник | Полезный механизм | Что есть в SEA после этой работы |
|---|---|---|

| [GEPA-Curator](https://arxiv.org/html/2610.37651v1) | Сначала определить, пригодна ли история для улучшения промпта; учитывать успешные примеры, а не только неудачи | Детерминированный фильтр исключает инфраструктурные сбои, незавершённые записи, неизвестный/ненадёжный verifier, изменённый исходник, секреты и противоречивые оценки одинакового результата. | [ACE](https://arxiv.org/html/2510.04618v1) | Обновлять отдельные элементы контекста, сохраняя накопленное; разделить генерацию, рефлексию и слияние | Кандидат добавляет максимум четыре коротких правила к исходному промпту. Существующие `ProjectContext` и `ContextBoard` уже объединяют небольшие записи под блокировкой и проверяют происхождение evidence — второй параллельный механизм памяти не добавлен. |
| [Pi, agent loop](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts), [LangSmith double texting](https://docs.langchain.com/langsmith/double-texting) | Отделять сообщение во время работы, следующий шаг и продолжение после завершения; явно задавать очередь/прерывание | Исправлено представление ожиданий: зависимость от задачи и дополнительный предикат хранятся отдельно. | [DSH prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) и предоставленная пользователем статья | Router принимает события, Workers исполняют изолированные задачи; компактные ссылки вместо общих огромных контекстов | Учтено в [проекте диспетчера](adr/0002-task-refinement-and-routing.md) и существующей оркестрации ветвей. Этот опыт не реализует постоянно работающий Router и не запускает Workers. |

Это собственная компактная адаптация отдельных механизмов. Пакет GEPA не установлен;
полный алгоритм GEPA не воспроизведён: нет многоитерационного выбора родителей,
скрещивания, оптимизации нескольких компонентов и предварительного отбора мутаций
на новых тренировочных rollout. Вместо обучаемого Curator — проверяемые фильтры.
Успешный пример в пилоте берётся из train, но это не полный поиск прошлых успехов
по тому же заданию. Метрики публикаций не переносятся на SEA.

## Конкретные изменения

- `src/eval/refinement.py`: описания полей отличают управление исполнением от
  требований; `wait_for.tasks` и `wait_for.predicate` могут сосуществовать у новой
  ожидающей задачи. Условная задача создаётся как `waiting`, не теряется в общем
  списке условий и не запускается преждевременно. Планировщик её пробуждения пока отсутствует.
- `src/eval/refinement_cases.py`: сохранена строгая метрика `exact`; добавлена
  `operation_match`. Дополнительный `context` допустим только как бездействие;
  лишнее `add`, неправильный приоритет или пропущенное намерение проваливают метрику.
  Runtime отдельно проверяет структуру, версии, цитаты, атомарность и повтор события.
- `src/eval/prompt_search.py`: фильтрация, ограниченная мутация, происхождение,
  защита от совпадающих входов между split, frontier по каждому примеру и фиксация
  выбора. Дельта ограничена четырьмя правилами по 450 символов; весь кандидат — 12000.
- `src/eval/refinement_holdout.py`: 6 validation-примеров и 12 test-примеров;
  другие формулировки, идентификаторы и предметные области. Идентичные входы
  обнаруживаются кодом, смысловую близость всех парафраз это не исключает.
- `scripts/refinement_search.py`: один живой раунд, три кандидата, максимум
  6 вызовов и бюджет 150000 токенов с предварительным резервированием. Нужен `--live`.
  Любой сбой прекращает опыт и оставляет `incomplete.json`, а не выдаёт успех.
- `tests/test_prompt_search.py`, `tests/test_refinement.py`: 39 целевых тестов,
  включая полный цикл с подставным backend, запрет передачи gold актору,
  фиксацию выбора до test и отсутствие автоматического продвижения в production.

Имеющийся [отбор конфигураций](pareto_search.md) решает другую задачу: качество/цена
повторных запусков, bootstrap и ограничения эксплуатации. Новый frontier сравнивает
векторы успеха по отдельным validation-примерам. Его выбор не является статистическим
доказательством превосходства и не заменяет прежний gate продвижения.

## Живые измерения

Использован авторизованный Codex CLI без собственных инструментов модели, как в
предыдущем опыте. Переданы только синтетические карточки и сообщения. Это не прямой
доступ к внутреннему API ChatGPT; ключи не извлекались. Модель CLI по умолчанию не
закреплена идентификатором, поэтому результаты нельзя приписывать Flash или 9B.

| Измерение | Результат |
|---|---:|
| Повтор 20 известных случаев с V2 и исправленной схемой | **20/20 exact**, 20/20 операция, сохранение требований и дедупликация |
| Validation исходного V1 с исправленной схемой | **6/6 операции**, 3/6 exact |
| Validation ручного V2 | **6/6 операции**, 6/6 exact |
| Validation отражённого кандидата | **6/6 операции**, 6/6 exact |
| Финальный test выбранного V1 | **12/12 операции**, **8/12 exact** |
| Полный pytest | **1372 passed, 3 skipped**, 12 предупреждений deprecation |

В четырёх несовпадениях test (`stop`, `after`, `both-waits`, `retract`) модель
добавила `context` с подтверждением уже известных сведений. Требуемые операции
сошлись, новых требований/отмен они не вызвали. Метрики определены до вызовов;
`exact` не подменена улучшенным числом задним числом. Первый результат **16/20**
из [6 ноября](refinement_research_20261106.md) сохранён.

Все кандидаты сравнялись по заранее выбранной метрике операций, и сработало правило
равенства: более короткий промпт. Поэтому выбран V1 с уточнённой схемой. Два новых
правила, предложенные отражающей моделью, соответствуют обнаруженным ошибкам:
не дублировать завершение зависимости в условии и не превращать сохранение
исполнения в новое требование. Они улучшили точность формы на validation, но
преимущества по правильности операций в этом пилоте **не показали**. В production
ни один кандидат автоматически не установлен. Длина текста — только правило
разрешения равенства, а не измерение полной цены выполнения.

Старая и новая регрессии отличаются также описаниями схемы и размером пакета
(3 → 6 независимых карточек за запрос). Это проверка совокупного исправления,
не чистая абляция одного промпта. Один небольшой синтетический прогон с проверкой
полей/подстрок не доказывает общее понимание намерения или качество SWE-bench.
Отложенный набор после этого опыта считается использованным; новую итерацию
нужно проверять на новом test, не подгонять под эти двенадцать ответов.

Расход: регрессия — **96901** токен (94780 входных + 2121 выходной), поиск —
**121396** (117478 + 3918); всего **218297 токенов, 11 вызовов**. В это входит
контекст оболочки Codex. Долларовая стоимость неизвестна, локального inference не было.
В обычном диалоге агента этот офлайн-контур добавляет **0 модельных вызовов**.

## Воспроизведение и артефакты

```bash
# Без модели: показать план.
.venv/bin/python scripts/refinement_search.py

# Старый набор + два настоящих последовательных уточнения.
.venv/bin/python scripts/refinement_eval.py --live --policy v2 --batch-size 6 \
  --output data/eval/my-new-regression

# Только в новом каталоге; явный запуск облачных запросов.
.venv/bin/python scripts/refinement_search.py --live \
  --output data/eval/my-new-search

.venv/bin/python -m pytest tests/test_refinement.py tests/test_prompt_search.py -q
```

`data/eval/refinement-fix-20261107/` содержит `regression/result.json`,
`search/protocol.json`, `curation.json`, `candidates.json`, `selection.json`,
отдельные validation/test-ответы, запросы и CLI receipts, `pytest.xml` и итоговую
сводку `result.json`. Исходники оценщика и разделение наборов хешированы до опыта;
выбор записан до первого test-вызова. Архивные train-ответы заново оценены текущим
зафиксированным оценщиком — это не заявление о неизвестных хешах исходников старого опыта.

Для применения к другим частям harness нужен адаптер, который исполняет конкретный
кандидат и даёт внешнюю проверку: профиль реализации → тесты; исследовательский
профиль → проверяемые факты; выбор инструментов → разрешённые действия и последствия.
Базовые ограничения доступа и политики безопасности не должны становиться
самоизменяемыми параметрами. Сохранение родительского текста само по себе не
гарантирует, что добавленное правило не противоречит ему; поэтому кандидат остаётся
офлайн-гипотезой, а проверку полномочий всегда выполняет runtime.
