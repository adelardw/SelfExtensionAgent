# develop.md — рабочий план развития (ориентир при разработке)

Идейная основа — CLAUDE.md (замкнутый контур). Диагноз: самая тонкая стадия контура —
«↓ сигнал» (implicit feedback). Порядок A → B → C → D выбран так: A питает сигналом всё
остальное, B — главный материальный выигрыш парадигмы, C почти бесплатен, D требует
ключей и пары платных прогонов.

Жёсткие рамки (из CLAUDE.md, не нарушать): ядро заморожено (только few-shots/факты/навыки/
ParamStore); роли вслух не упоминать; онбординг по ходу исполнения; бюджет ~$15 — дорогие
прогоны только по явному слову; решения универсальны, не костыльны.

## A. Единый журнал взаимодействий → настоящий implicit feedback   ✅ СДЕЛАНО (2026-06-12)

**Идея.** Схема контура: сигнал рождается из подтверждений действий, выбора пунктов плана,
HITL, уточнений. Эти события УЖЕ происходят (hitl.py, clarify-реестр, user_blocked), но
умирают в конце прогона. Сейчас implicit feedback = только эвристика [neg] по следующему
сообщению.

**Что сделать.**
1. Журнал событий взаимодействия за прогон (interaction ledger): HITL-разрешения/отказы
   (с описанием действия), ответы на уточнения (вопрос→ответ), user_blocked.
2. `reflect` пишет события в эпизод (вместе с trajectory).
3. Harvest превращает события в персонализацию:
   - HITL-отказ → факт профиля («не делать X без спроса») + few-shot осторожности;
   - clarify-ответ → факт профиля (онбординг-по-исполнению становится НАКОПИТЕЛЬНЫМ);
   - паттерн отказов → сигнал для per-user backward.
4. Ноль LLM-вызовов в горячем пути — всё в уже существующем reflect/harvest.

**Готово, когда:** события переживают прогон, видны в эпизоде, конвертируются в
факты/few-shots, покрыто тестами (отказ HITL → факт появился; clarify-ответ → факт появился).

**Реализация:** `src/interaction.py` (ledger-contextvar по образцу clarify + harvest без LLM);
`hitl.confirm` пишет решения (deny-by-default без канала НЕ пишется — это не выбор юзера);
эпизоды получили колонку `interactions` (JSON: HITL + clarify) — сырьё для B/C;
`recall` сбрасывает журнал, `reflect` сохраняет в эпизод и харвестит:
HITL-отказ → факт `hitl-отказ: <skill.tool>` (upsert — повторы не плодят дублей),
clarify-ответ (только answered) → факт `уточнение: <вопрос>`. Тесты: tests/test_interaction.py.

## B. Привычки: траектория → навык (само-расширение из повторов)   ✅ СДЕЛАНО (2026-06-12)

**Идея.** Само-расширение сейчас реактивное («нет способности → создать»). Парадигма
требует конвертировать ПОВТОРЯЮЩИЕСЯ дорогие deliberate-прогоны юзера в дешёвые
персональные навыки: «способность=цель, бюджет=констрейнт» + «универсальность = сумма
персонализаций» буквально.

**Что сделать.**
1. Reflect ищет k похожих успешных эпизодов юзера (векторная близость query+плана — уже есть).
2. Триггер дистилляции: план+шаги траекторий → параметризованный навык через существующую
   create_skill-ветку (smoke-тест обязателен).
3. Навык помечается как персональный; skill_selector подхватывает → задача этого типа у
   ЭТОГО юзера идёт быстрым/дешёвым путём.
4. Анти-оверфит: навык — обобщение k траекторий (параметры, не константы одного кейса).

**Готово, когда:** на синтетике (3 похожих эпизода) дистиллируется навык, проходит smoke,
выбирается selector'ом; тест без живого LLM (мок) + один живой прогон по слову юзера.

**Реализация (через существующие каналы, без новых LLM-путей и правки графа):**
`src/habits.py` + `MemoryStore.similar_successes`. Цикл: reflect после успешного
deliberate/heavy-прогона видит ≥HABIT_K (конфиг, дефолт 3) похожих успехов → пишет
факт-директиву «привычка: …» (importance 0.75) → recall инъектирует её в memory_context →
router (новое правило ИСКЛЮЧЕНИЕ-ПРИВЫЧКА в промпте) выбирает create_skill → существующая
ветка создаёт навык под всеми защитами (SGR-ревью+smoke) → reflect закрывает привычку (✅,
повторно не флагуется). В eval выключено (анти-оверфит). Дедуп кластера — Jaccard по ключу
факта. Платный шаг один и только в уже существующей ветке. Тесты: tests/test_habits.py.
Живой сквозной прогон (3 повтора → навык) — по явному слову юзера (бюджет).

## C. Per-user приоры выбора через бандитов   ✅ СДЕЛАНО для режимов (2026-06-12); selector — позже

**Идея.** Beta-Thompson на выбор режима reflexion / навыка / тула: ручка = (тип задачи →
режим/навык), reward = существующий validation-исход эпизода. Ноль LLM-затрат. Против
разреженности — та же двухъярусность, что у few-shots: глобальный prior + персональный
оверлей. Ядро не трогается: бандит крутит только ВЫБОР, не промпты.

**Готово, когда:** хранилище счётчиков (ParamStore-стиль), сэмплирование подмешивается в
reflexion/selector как prior (не диктат), деградация к текущему поведению при пустых
счётчиках, тесты на сходимость на синтетике.

**Реализация (режимы):** `src/bandit.py` + `MemoryStore.similar_episodes`. Хранилище
счётчиков НЕ понадобилось — эпизоды и есть счётчики (mode+outcome), нет второго источника
правды. Контекст ручки = кластер похожих запросов (Jaccard, как habits/feedback). Ключевая
ниша: few-shots харвестятся только из успехов — бандит добавляет НЕГАТИВНОЕ свидетельство
(«fast тут 0/4»). Beta(1+succ,1+fail) + Thompson → строка-прайор в существующий слот
memory_context reflexion (ядро не тронуто, прайор ≠ диктат). <3 наблюдений → '' →
поведение без изменений. Тесты: tests/test_bandit.py (сходимость, отсутствие утечки чужих
кластеров). Осталось из C: тот же прайор для skill_selector/ToolSearch (по полю skills
эпизода — данные уже пишутся) — взять после D или по слову юзера.

## E. Браузер-первичность + act-режим + заземление действий   ✅ СДЕЛАНО (2026-06-12)

**Триггер:** живой прогон «Открой яндекс почту» — почта не открылась, контекст сгорел
(15k токенов), валидация приняла слова за дело. Диагноз по трейсам, три причины:

1. **Регрессия `_is_web`** (корень): веб-шаг определялся по `"search" in имя_тула`, а
   `search_memory`/`search_knowledge_base` прицеплены к КАЖДОМУ шагу → каждый шаг (даже
   «открой почту») шёл в тяжёлый agentic research вместо прямого действия. Фикс: `_web_step()`
   — по ВЫБРАННЫМ НАВЫКАМ, не по именам тулов. Регрессионный тест.
2. **Текст ≠ действие**: по-пунктовый валидатор не видел, вызывались ли инструменты.
   Фикс: в step-валидацию передаётся список РЕАЛЬНО вызванных тулов + правило «действие
   без вызова инструмента = не выполнено».
3. **Браузер-первичность** (решение юзера): интерактивный веб (открыть сайт/почту/кабинет,
   всё где нужны его логины) — через РЕАЛЬНЫЙ браузер юзера (`open_url` с конкретным URL
   сервиса + analyze_screen/type_text при необходимости); headless-поиск (search_web/fetch/
   deep_research) — ТОЛЬКО фоновый сбор информации. Зашито в step_execution, act-промпт и
   device_control.md.

**act-режим (6-й тип мышления, «System 1 с руками»)**: простое прямое действие → reflexion
выбирает act → BM25-подбор навыка по полным md (без LLM-селектора) → `_exec_direct` (1–2
вызова, HITL-обёртки сохранены) → reflect. Ни одного вызова тула или ESCALATE → эскалация
в deliberate через goal. Тяжёлый пайплайн — только когда прямого действия не хватает
(требование юзера). Тесты: tests/test_act_mode.py.

**Бандит под флагом**: `agent.bandit_prior` (конфиг, дефолт true) — юзер справедливо
напомнил, что это гипотеза; выключается одной строкой, критерий проверки — см. C.

## F. АРХИТЕКТУРНЫЙ ПРИНЦИП: «амортизированный агент»   [ядро ✅ 2026-06-12, доказательство — по слову юзера]

**Диагноз текущей архитектуры.** Она хорошо обучаемая (forward/backward по графу — это
реально отличительно), но как у ВСЕХ известных паттернов (ReAct, plan-execute, reflexion,
multi-agent) её предельная стоимость задачи ~ПОСТОЯННА: сотая похожая задача стоит столько
же LLM-вызовов, сколько первая. Фикс-пайплайн жжёт одинаковый оверхед на каждый прогон.

**Принцип (наше «принципиально новое», честно: новая КОМБИНАЦИЯ + измеримое утверждение).**
Каждый успешный прогон ОБЯЗАН оставить артефакт, делающий похожие задачи дешевле. Лестница
компиляции опыта: эпизод → few-shot → РЕЦЕПТ (план+навыки) → привычка → НАВЫК (код).
Плюс лестница исполнения с проверяемой эскалацией (вместо угадывания режима наперёд):
рецепт-replay → act → deliberate → heavy, ступень вверх — только по ПРОВЕРЕННОМУ провалу
(заземление: вызовы тулов, win/lose рецептов), ступень вниз — по компиляции опыта.
Это и есть «персонализация как метод» из CLAUDE.md, доведённая до архитектурного принципа:
агент СТАНОВИТСЯ дешевле и быстрее именно для своего пользователя.

**Измеримое утверждение (фальсифицируемое, дёшево проверяемое):** кривая стоимость/время
на задачу ПАДАЕТ с числом эпизодов при не худшем качестве. Проверка —
`scripts/amortize_bench.py`: один список задач × 2 прохода на одном user_id (cold vs warm);
тезис подтверждён, если pass-2 дешевле/быстрее при не худшей confidence. ПЛАТНЫЙ прогон —
только по явному слову.

**Ядро реализовано — РЕЦЕПТЫ (ступень-0):** `MemoryStore.recipes`
(add/find/get/feedback): успешный deliberate/heavy-прогон компилируется в рецепт
(план+навыки, дедуп по похожести); похожая задача (Jaccard ≥0.55) → селектор БЕЗ LLM-вызова
из рецепта, decompose получает проверенный план через слот capability_hint (шаблон ядра не
тронут); win/lose-трекинг, систематически проигрывающий рецепт самоудаляется.
Тесты: tests/test_recipes.py. Уже были: эскалация act→deliberate (E), привычка→навык (B),
бандит-прайор (C), few-shots (improve/) — рецепты замыкают лестницу.

**Живой прогон №1 (2026-06-12): тезис НЕ подтвердился** — warm +13% токенов, +19% времени
(cold 87k tok / $0.0103 / 268с / conf 78% → warm 98k / $0.0126 / 319с / 76%). Честный
разбор (отрицательный результат = данные):
1. ложный «переспрос слабого»: «саммари ARCHITECTURE.md» сматчился (Jaccard 0.35-гейт) со
   слабым «саммари README.md» → негативный сигнал заблокировал компиляцию рецепта и толкнул
   исполнителя «зайти иначе» (49с→130с, +14k tok). Фикс: _REPEAT_SIM 0.35→0.55;
2. рецепт экономил только селектор, а warm добавлял контекст в каждый вызов и НЕ скипал
   capability_research. Фикс: рецепт → скип capability_research (способность доказана);
3. дисперсия > дельты при n=4 несвязанных задач. Фикс: парные per-task дельты в бенче,
   семейства задач без лексических пересечений.
Прогон №2 — упал на транзиентном APIConnectionError (reason_node без защиты ронял весь
граф; бенч умирал целиком). Фиксы: reason_node crash-safe (пауза+повтор → честный отказ),
бенч переживает сбой одной задачи.

**Прогон №3: рецепты сработали на всех deliberate-задачах (селектор без LLM ×3,
capability_research скип), НО**: токены всё равно +12% (парно +5..+21%), а вот
НАДЁЖНОСТЬ выросла сильно — conf 76%→98%, задача-неудачник 18%→95%. Урок (ключевой
для принципа): **артефакт должен ЗАМЕНЯТЬ работу, а не аннотировать её** — хинты/few-shots/
прайор раздували контекст каждого из ~8 вызовов и съедали экономию двух дешёвых вызовов.
Фиксы: (а) sim≥0.7 → план берётся ИЗ рецепта, decompose БЕЗ LLM-вызова вообще;
(б) few-shots шага k=3→1 при рецепте. Прогон №4 — проверка.

**Прогон №4 (replace-not-annotate): ТЕЗИС ПОДТВЕРЖДЁН по токенам и качеству.**
cold 80.7k tok / $0.0101 / conf 78% → warm 70.2k / $0.0088 / conf 98%: **токены −13%,
качество +20 п.п.** Парно: рецептные задачи −19% и −26% tok; нерецептная reason-задача
+10% (на ней был сетевой повтор — но conf 18%→95%). Honest-оговорки: (1) n=4, нужна
серия для статистики; (2) ВРЕМЯ в этом прогоне хуже (+58% — латентность API/троттлинг
провайдера доминирует над числом вызовов; мерить медианой по повторам); (3) conf —
самооценка валидатора, не внешняя разметка. Итог трёх честных итераций: артефакты,
ЗАМЕНЯЮЩИЕ LLM-работу, дают и дешевле и надёжнее; аннотирующие — только надёжнее.

**Дальше (по слову юзера):** обратное направление лестницы (deliberate→act для задач с
устойчивым рецептом из 1 шага); рецепты в reflexion (старт со ступени рецепта, не с
предсказания режима); few-shots/прайор скипать при рецепте (ещё меньше тёплый контекст).

## G. Коллективные рецепты — «рекомендательная система поведения»   ✅ ядро (2026-06-12)

**Идея юзера:** автоматизация повторяющихся сложных задач — не только per-user: из многих
пользователей формируются best-practices внутри ассистента; похожим людям — примерно одно
и то же поведение агента (рекомендательная система: item=рецепт, фичи юзера=роли профиля).

**Реализация:** `src/collective.py`. Личный рецепт, доказавший себя (uses≥2, winrate≥0.66),
промоутится в общий пул инсталляции (`user_id='__global__'`) с отпечатком профиля источника
(значения роль-фактов). Новый юзер без своего рецепта получает коллективный: похожесть
запроса (≥0.55) + профиль-гейт (Jaccard≥0.08, мягкий: пустые профили пропускаются —
cold-start по запросу). Защиты: личное > коллективное; промоушен только проверенного
(один юзер не отравит всех); инъекционные запросы не промоутятся (не учиться на взломе);
win/lose глобальных копится дальше — не работающий у «похожих» рецепт самоудаляется
(дрейф тонет); в eval промоушена нет (анти-оверфит); пул в локальном SQLite, наружу не
уходит. Тесты: tests/test_collective.py.

**Дальше (по слову юзера):** LLM-генерализация при промоушене (личные параметры запроса →
плейсхолдеры; privacy в мульти-юзер деплое); тот же двухъярусный паттерн для привычек;
профиль-матчинг по эмбеддингам вместо Jaccard при появлении объёма.
